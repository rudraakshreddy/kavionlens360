1. The problem

Banks store activity as transactions, but managers think in customers. With limited relationship-manager time, a raw transaction log cannot say who to focus on, why, with what offer, where they are, and how large the opportunity is.

This project builds a small analytical version of a Customer 360: a reconciled customer table, behaviour segments with a named action each, and a ranked opportunity list, delivered through SQL, Python, Power BI, an Excel MIS and an executive deck.

Value chain: data → analysis → insight → business action.

  1. PostgreSQL 16: staging, 17 cleaning rules, star model, customer_360
  2. Python: profiling, EDA, statistics, K-Means segmentation, opportunity scoring
  3. Power BI (5 pages), Excel MIS (7 sheets), deck (8 slides), this site
  4. Reconciliation: SQL = Python = Excel = Power BI, variance 0

2. Data, profiling and quality

Profiling the 1,048,567-row file confirmed every published count, and found two issues the dataset page does not mention:

Coverage ends on 15 September

Every day from 1 Aug to 15 Sep has roughly 17–27K transactions; after that the file holds only a few scattered days. Because recency and “active” rules need complete coverage, the analysis window was fixed to 46 days and the sparse tail (58,826 rows) was logged, not silently dropped.

CustomerID is not a stable person key

Only 0.9% of repeat CustomerIDs keep the same birth date, gender and city across their rows. The ID is kept as the key (as specified), conflicts are resolved by the most-frequent-then-latest rule, and repeat-customer features are interpreted with care.

3. Customer 360 insights

Value is extremely concentrated

The top 1% of customers generate 27% of transaction value, the top 10% generate 63% and hold 77% of balances (Gini 0.74).

Most customers appear once

84.6% of customers made a single transaction in the window, so frequency is weak evidence for most of the base. Every list carries an evidence level.

Metros carry the book

Mumbai, New Delhi, Bangalore, Gurgaon, Delhi hold 42% of value. Weekend days run 22% above weekdays, and 63% of activity falls between 12:00 and 21:00.

Statistics, with effect sizes

With 840K customers every test is “significant”, so each reports an effect size. The result is consistent: behaviour, not demographics, explains value. Gender barely moves ticket size (rank-biserial r = 0.08), age explains little of balance (ε² = 0.06), metro status barely changes the high-value share (Cramér's V = 0.05), while balance and transaction value are only moderately linked (Spearman ρ = 0.30).

4. Five behaviour segments

K-Means on five behaviour features (log balance, log value, log ticket, capped frequency, recency), with k chosen from 3–10 by elbow, silhouette, Calinski-Harabasz and five-seed stability. k = 5: silhouette 0.279, ARI ≥ 0.93, smallest segment 9.5%. Gender and city were excluded from the inputs and only used to profile.

5. Cross-sell opportunity signals

Signals inferred from behaviour; product ownership is unknown. Six transparent rules use percentile thresholds. Each customer gets a score: 100 × (0.35 value + 0.25 engagement + 0.30 rule fit + 0.10 recency), and tiers A (top 5%), B (next 15%), C (next 30%) and Watch. These rank conversations; they are not eligibility or credit decisions.

7. Limitations and responsible use

  • Public data from one bank in 2016 and a 46-day window: no seasonality, trend or tenure claims.
  • No product holdings, revenue or campaign outcomes: opportunity is a signal, value is a proxy (balance and activity).
  • CustomerID is not a stable person key in this extract; repeat behaviour is weak evidence.
  • Clusters describe behaviour; they do not predict it.
  • Age is used only as a life-stage hint; gender and city are never model inputs. Flags start conversations; they never decide eligibility.

Version 2

  • Add product holdings and campaign response to build propensity models and measure lift.
  • Longer time window and entity resolution for a reliable customer key.
  • Segment-drift monitoring and fairness checks on every refresh.
